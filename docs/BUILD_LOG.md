# 制作记录

## 2026-10-23：先把流程收成一个项目

从日常图文发布中遇到的分段、上传、AI 声明和回执问题出发，决定单独整理一个本地工具。

今天完成的是立项范围、本地 Git 仓库和 GitHub 公开仓库。第一步先让一份文案和图片自动填好预览，逐项核对后停住。浏览器适配器、真实页面验收与最终提交都尚未实现。

已有开源实现可以参考。接下来先检查其适用程度，再决定复用哪一层；开发记录会保留这些实际选择。

名称确定为 Redlet，仓库名 redlet；许可证采用 Apache-2.0。公开仓库：https://github.com/Jarmck-Cai/redlet 。浏览器预览适配仍待实现。

## 2026-10-23：第一份预览跑通

上游有现成的 Go 发布工具，也有能只填表的 Python 脚本。我们参考了它们的页面操作，自己补上素材包读取、正文分段和回读。

真实页面比测试页多了一个几乎透明的“上传图文”副本。账号已经显示，页签还没加载完，第一次就停在了这里。另一个细节是图片上传没有 Content-Type；只按文件类型监听请求，会漏掉已经完成的上传。两个差异都补回了测试。

最后用两张编号图片跑通了 Rednote 预览，正文里的空行、<tag> 和 & 留了下来。图片响应与缩略图摘要、AI 声明和仅自己可见设置也已核对。程序保存截图后关闭窗口，没有提交笔记。

[验收记录](VERIFICATION.md)和[示例截图](assets/rednote-preview.png)已保存。

## 2026-10-23：用 Redlet 发自己的开发记录

把预览接到实际提交后，先遇到的是结果查询。搜索会切到已发布，切换审核页签又会清空搜索；初始化还有一次全部列表请求。按静态测试页的顺序操作，会把查询重置掉。现在已发布用标题搜索和卡片视图核对，审核或未通过只定位当前页里本篇的精确标题。

最终发布按钮也和测试页不同。它在 xhs-publish-btn 的封闭组件里，里面并排放着暂存和发布。Redlet 仅读取该组件内真正发布按钮的状态和边界，再发送普通鼠标点击；两个动作分开做了Chrome回归。首次实跑在识别处停止，没有提交。修正后用同一内容ID完成一次提交。

这次发的是《为了发开发记录，又做了个工具》。纽约14:57得到提交确认，随后核对为审核中；15:00用新进程verify复查仍为审核中，提交时间保持。61项测试、类型检查和构建通过。[验证记录](VERIFICATION.md)保存实际时刻，尚未取得公开直达链接。

## 2026-10-24：查询没找到时，保留上次确认的结果

样例图文提交后，第一次看到了审核中，随后两次独立查询却没找到目标。旧记录会改成待核对，留下原来的核实时间，却没有单独记下那时确认了什么、这次什么时候查过。程序仍会拦住重发，但读记录需要回头找截图。

这轮把两件事分开保存：本次查询仍可能待核对，上次确实看到的状态和时间另外保留；新结果确认后再更新。异常退出也留下同样的结构化结果。增加了只读本地记录的 status 命令，看上次进度不用再启动Chrome，需要最新状态时才运行verify。

先以受控任务文件复现历史信息缺失，再补实现。审阅时另补了浏览器启动前失败的回归：用临时普通文件阻住配置目录，确认旧处理没有输出任务结果，新处理会保留确认状态、提交时间并释放锁；这项测试不连接真实平台。

实际对同一篇样例图文运行verify，已核实发布。纽约15:06用旧构建先查到，15:13用新构建再次查到相同笔记ID与原提交时间；随后status读到相同的本地结果。这轮没有再次提交笔记。此前两次没找到的页面原因未在这轮复现，本次修正的是记录和结果输出。

## 2026-10-28：合并前补齐跨状态的同名保护

准备将开发分支合并供人试用时，审查发现首次结果核对可能先认到已发布的旧同名笔记，而跳过审核中的新笔记。受控页面复现后，先补四项会失败的回归，再让首次标题定位检查三个当前加载视图；同名、缺ID或回到目标时ID变化均保留待核对。唯一候选按观察到的ID再次核对后才确认。
